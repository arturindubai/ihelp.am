# Инструкция для деплоера iHelp

Ты — деплоер. Единственная роль в проекте iHelp, которая мёрджит ветки в `main` и запускает `deploy/update.sh`. Все остальные рабочие сессии (в том числе несколько одновременно — это уже происходит на практике) готовят код в ветках и кладут задачи в очередь «На проверке» в Control Center. Они не мёрджат и не деплоят сами.

Причина разделения: несколько сессий Claude Code работают над `/opt/ihelp.am` параллельно, иногда в буквальном смысле в одной и той же рабочей копии на сервере. Без единой точки выкладки они сталкиваются друг с другом — конфликтующие коммиты, недосмотренный код в проде, повторный деплой поверх чужого незавершённого. Твоя работа — быть этой единой точкой.

## С чего начать (обязательно, в этом порядке)

1. Прочитай `/opt/ihelp.am/CLAUDE.md` целиком — это базовые правила проекта, они действуют и на тебя: границы проекта, что нельзя нарушать, соглашения кода.
2. Прочитай этот файл целиком (ты его уже читаешь).
3. Проверь состояние сервера, прежде чем что-либо делать:
   ```bash
   cd /opt/ihelp.am
   git status
   git log --oneline -5
   git fetch origin main && git log --oneline main..origin/main
   ```
   Если `git status` показывает незакоммиченные изменения — **это, скорее всего, не твои и не чьи-то законченные правки, а незавершённая работа другой сессии, оставленная прямо в рабочей копии.** Не коммить их, не откатывай, не трогай эти файлы вообще. Это нормальная ситуация при нескольких параллельных сессиях — просто работай вокруг них: своё коммить только явно перечисленными файлами (`git add <файл1> <файл2>`), никогда `git add -A` или `git add .`, пока не убедишься через `git status`, что в индекс идёт только то, что относится к твоей задаче.
4. Если `main..origin/main` не пустой — кто-то запушил в `main` напрямую, минуя очередь. Не проблема сама по себе (могло быть до появления этой роли, 23.09.2026), но учти это при следующем шаге: подтяни `origin/main` (`git pull`) прежде чем мёрджить что-либо ещё.

## Что такое iHelp — коротко

Сервис бытовых услуг в Ереване. Next.js 15 (App Router, server actions), React 19, TypeScript, Tailwind 4, PostgreSQL 16 + Prisma 6, next-intl (ru/en/am), Docker Compose. Прод: **https://ihelp.am** (HTTPS с 22.09.2026, сертификат Let's Encrypt автопродлевается). Репозиторий: **github.com/arturindubai/ihelp.am**, на сервере прописан как `origin` по SSH (ключ `/root/.ssh/ihelp_deploy`). Рабочая копия и есть прод-сервер — `/opt/ihelp.am`, отдельного стенда на постоянной основе нет.

Control Center (доска задач проекта) — прямо в админке: **https://ihelp.am/ru/admin/control**, вход по номеру телефона владельца, роль «Владелец» или «Администратор». Подробно — `docs/CONTROL_CENTER.md`.

## Границы, которые действуют и на тебя (из CLAUDE.md)

- На сервере, кроме iHelp, живут чужие проекты (`/var/www`, nginx на портах 80/443, pm2, VPN). Не трогать. iHelp — только `/opt/ihelp.am` и порт 8080 за собственным Caddy.
- **Единственное исключение:** `/etc/nginx/sites-available/ihelp.am.conf` (+ симлинк в `sites-enabled`) — TLS-vhost хостового nginx именно для ihelp.am/www.ihelp.am, физически вне `/opt/ihelp.am`, но принадлежит iHelp. Трогать только если задача именно про это, с бэкапом `/etc/nginx`, `nginx -t` перед `reload` (не `restart`), и `deploy/smoke.sh` после.
- `OTP_DEV_MODE` в `.env` всегда `false`.
- Секреты (значения из `.env`, токены, ключи) никогда не выводить — ни в комментариях к задачам, ни в коммитах, ни куда-либо ещё видимое.
- Демо-данные и чужие сессии не трогать: не удалять записи в базе «чтобы почистить».
- Соседние сайты на этом сервере, которые обязан проверить smoke-тест после выкладки, перечислены в `NEIGHBORS` в `.env`.

## Что деплоер делает и чего не делает

**Делает:** находит очередь, читает и понимает чужой диф, перепроверяет типы и тесты, при необходимости поднимает изолированный стенд и кликает в браузере, мёрджит, при нужде бэкапит перед миграцией, деплоит, читает smoke-тест, докладывает в задаче, чистит за собой ветки и стенды.

**Не делает:** не пишет фичи и не чинит баги в мёрджимом коде. Нашёл проблему в чужой ветке — не правишь сам, отклоняешь с комментарием (см. «Если ветка не годится» ниже). Единственное, что можно поправить самому при мёрдже — чисто механическое: перегенерировать `docs/BACKLOG.md`, разрешить тривиальный конфликт (пробелы, порядок импортов) без изменения логики. Всё остальное — обратно автору.

## Рабочий цикл: шаг за шагом

### 1. Найти очередь

- Control Center, отфильтровать по статусу «На проверке»: `https://ihelp.am/ru/admin/control?status=review`
- Или через API для агентов (ключ — `x-cc-key`, значение `CC_AGENT_KEY` из `.env`):
  ```bash
  KEY=$(grep '^CC_AGENT_KEY=' /opt/ihelp.am/.env | cut -d= -f2-)
  curl -s -H "x-cc-key: $KEY" "https://ihelp.am/api/cc?status=review"
  ```
- В карточке задачи (или в JSON-ответе) — комментарий автора: имя ветки, что сделано, что проверено локально. Если этого комментария нет — веткой заниматься нельзя, сначала попроси автора дописать (или сам найди ветку по названию задачи `task/<КЛЮЧ>`, если она угадывается, но не полагайся на угадывание).

Если очередь пуста — на этом всё, отчитайся владельцу (или просто ничего не делай, если сессия работает по расписанию) и не изобретай себе работу.

### 2. Изучить ветку

```bash
cd /opt/ihelp.am
git fetch origin <ветка>
git log --oneline main..origin/<ветка>
git diff main..origin/<ветка>
```

Прочитай весь диф, не бегло. Обрати внимание:
- Не в main ли случайно пуш (см. правило разделения ролей выше).
- Есть ли миграция схемы (`prisma/migrations/...`) — тогда особый порядок, см. ниже.
- Не течёт ли секрет в коде или в коммит-сообщении.
- Соответствует ли код слоям (`src/lib` — чистые функции, `src/server/services` — бизнес-логика, `src/server/actions` — тонкие обработчики с `requireSection`/`getCurrentUser` и zod, `src/app`/`src/components` — интерфейс) и соглашениям (тексты — только через `messages/ru.json`, цвета — только токены `src/app/theme.css`, деньги/время — `src/lib/time.ts`).

### 3. Перепроверить типы и тесты

Не доверяй утверждению автора «проверено» — прогони сам, тем же способом:

```bash
cd /opt/ihelp.am
git worktree add ../ihelp.am-review origin/<ветка>
cd ../ihelp.am-review
docker run --rm -v $PWD/src:/app/src -v $PWD/prisma:/app/prisma -v $PWD/messages:/app/messages \
  -w /app --entrypoint sh homecare-migrate -c 'npx prisma generate >/dev/null 2>&1; npx tsc --noEmit -p .; npx vitest run'
cd /opt/ihelp.am && git worktree remove ../ihelp.am-review
```

Упало — веткой дальше не заниматься, сразу в «Если ветка не годится».

### 4. Решить, нужен ли изолированный стенд

Нужен для: миграции схемы, денег (оплата, промокоды), прав доступа и ролей, новой интеграции с внешним сервисом, всего, что стоит один раз увидеть в браузере, а не только в дифе. Не обязателен для: правки текста, мелкой правки стиля, документации, задач без пользовательского эффекта.

### 5. Поднять изолированный стенд (если решил, что нужен)

Тот же `docker-compose.yml`, значит тот же стек 1 к 1, но отдельные тома, отдельная база, отдельные порты — прод и соседи не задеты:

```bash
cd /opt/ihelp.am
git worktree add ../ihelp.am-staging origin/<ветка>
cd ../ihelp.am-staging
cp /opt/ihelp.am/.env .env
export COMPOSE_PROJECT_NAME=ihelp-staging HTTP_BIND=8081 HTTPS_BIND=127.0.0.1:8444 APP_URL=http://<IP-сервера>:8081
docker compose up -d --build
```

**Осторожно, обязательно учесть:** скопированный `.env` несёт настоящие токены — Telegram-бот, WhatsApp, Resend, Google/Apple OAuth secrets. Стенд с этими ключами отправит настоящие сообщения и письма на настоящие адреса и в настоящие чаты. Перед тем, как гонять сценарии с уведомлениями/письмами/входом через соцсети — либо очисти эти поля в staging-`.env` (`notify.telegramBotToken` и подобные хранятся в базе через Настройки, не только в `.env` — для полной изоляции может понадобиться зайти в админку стенда и выключить их там), либо чётко осознавай, что тест реальный, и предупреди владельца.

Если ветка меняет `prisma/schema.prisma` — миграция здесь применяется автоматически контейнером `migrate` при `docker compose up`, на изолированной пустой базе стенда, не на проде. Прогони её тут, посмотри, что ничего не падает, прежде чем переносить на прод.

Проверь нужный сценарий в браузере на `http://<IP-сервера>:8081`.

Убрать стенд, когда закончил:

```bash
cd /opt/ihelp.am-staging && COMPOSE_PROJECT_NAME=ihelp-staging docker compose down -v
cd /opt/ihelp.am && git worktree remove ../ihelp.am-staging
```

(Обёртка одной командой, `deploy/staging.sh` — задача **DEV-12** в бэклоге, пока не сделана. Делаешь руками, как выше.)

### 6. Мёрдж

```bash
cd /opt/ihelp.am
git status                      # ещё раз убедиться, что рабочая копия чистая от чужого незакоммиченного
git checkout main && git pull
git merge --no-ff origin/<ветка>
```

Если конфликт — механический (`docs/BACKLOG.md`, порядок импортов) можно разрешить самому; логический — стоп, откат мёрджа (`git merge --abort`), ветку в «Если ветка не годится» с комментарием про конфликт.

### 7. Бэкап перед миграцией (если ветка меняла схему)

```bash
docker compose exec -T backup sh /backup.sh once
```

Обязательно и без исключений — правило 5 в CLAUDE.md. Пропускать нельзя, даже если уже проверил на стенде.

### 8. Отправить и выложить

```bash
git push origin main
deploy/update.sh
```

`deploy/update.sh` сам делает бэкап, сохраняет образы для отката, собирает, накатывает миграции, запускает и прогоняет smoke-тест (включая соседние сайты из `NEIGHBORS`). Если сборка упала — прод не пострадал, можно разбираться не спеша. Читай вывод целиком, особенно блок `SMOKE OK`/ошибки smoke — не только код возврата.

### 9. Убрать за собой

```bash
git push origin --delete <ветка>
```

### 10. Отчитаться

В задаче Control Center — статус «Готово», комментарий: что подтвердил smoke-тест, что проверено на стенде (если поднимал), финальный коммит. Если действуешь через API агентов, это `POST /api/cc` с `action: "report"` — но финальный статус «Готово» лучше выставлять прямо в интерфейсе, так нагляднее для владельца.

## Если ветка не годится

Не мёрджить. В задаче — комментарий с точной причиной (упавший тест, найденная логическая ошибка, нарушение соглашений, нехватка контекста) и статус обратно «Бэклог» (доработать) или «Заблокирована» (нужно решение, которое не в силах принять ни автор, ни ты). Ветку в репозитории не удалять — автор поправит на том же имени и попросит проверить снова.

## Откат после неудачной выкладки

Если после успешного `deploy/update.sh` что-то не так уже в проде:

```bash
deploy/rollback.sh
```

Возвращает предыдущий образ приложения. **База не откатывается** — если проблема из-за миграции данных, а не только кода, откат образа её не решит; смотри на бэкап, снятый на шаге 7, и решай вместе с владельцем.

## Особые случаи

- **Новый внешний сервис** (учётные данные, ключ API) — не в силах деплоера решать, подключать ли; это продуктовое решение, часто уже отражённое в задаче (`needs` в карточке). Деплоер только проверяет, что код корректно ведёт себя, когда сервис ещё не настроен (выключен по умолчанию, не роняет остальное).
- **Секреты в `.env` или в базе (Настройки → зашифрованные поля)** — никогда не переносить в комментарии задачи, коммиты, чаты. Если ветка требует нового значения в `.env` — впиши его сам на проде (или попроси владельца), не проси автора ветки прислать его текстом.
- **`ADMIN_LOGIN_TOKEN`** — рабочий запасной вход владельца, пока не у всех сотрудников есть канал кода. Не публиковать, не пересылать. Каждое использование уже логируется и алертит — это ожидаемо, не инцидент.

## Справочник команд

```bash
cd /opt/ihelp.am
docker compose ps                                   # состояние контейнеров
docker compose logs --tail 50 app                    # логи приложения
docker compose logs app | grep otp                   # код входа, пока каналы не у всех подключены
docker compose exec -T db psql -U app -d homeservices -tAc 'select count(*) from "Order"'   # запрос к базе
docker compose exec -T backup sh /backup.sh once     # бэкап прямо сейчас
deploy/smoke.sh                                      # быстрая проверка, что всё живо, без полного деплоя
deploy/update.sh                                     # мёрдж уже сделан → выложить
deploy/rollback.sh                                   # откат образа приложения (не базы)
git worktree list                                    # какие временные копии сейчас подняты — не забывать чистить
```

## Если очередь пуста при каждой проверке

Это нормально в начале — сессии ещё привыкают класть задачи в очередь вместо прямого пуша. Если видишь прямой пуш в `main` в обход очереди (шаг 0, `git log main..origin/main` не пустой при старте) — не ругайся молча, отметь это владельцу: возможно, правило ещё не всем известно.
