# Инструкция для деплоера

С 23.09.2026 в проекте разделены роли: **рабочие сессии** готовят код и кладут задачи в очередь на проверку; **деплоер** — единственная роль, которая мёрджит в `main` и запускает `deploy/update.sh`. Деплоером может быть отдельная рабочая сессия, назначенная на эту роль, или сам владелец. Причина разделения: несколько сессий работают над iHelp параллельно (это уже происходит на практике — видно по чужим коммитам в `git log`), и прямые пуши в `main` с немедленным деплоем каждой из них увеличивают риск столкнуться друг с другом или выложить недосмотренное.

## Что делает рабочая сессия (не деплоер)

Полный порядок — в `CLAUDE.md`, раздел «Рабочий цикл». Коротко: код → локальная проверка (`tsc`, `vitest`) → ветка `task/<КЛЮЧ>` или `work/<кратко>` → пуш ветки (не `main`) → задача в Control Center получает статус «На проверке» с комментарием: что сделано, что проверено локально, имя ветки. Дальше — работа деплоера.

## Как найти очередь

- Control Center, фильтр «На проверке»: `https://ihelp.am/ru/admin/control?status=review`
- Или через API для агентов: `curl -s -H "x-cc-key: $KEY" "https://ihelp.am/api/cc?status=review"`
- В карточке задачи — комментарий автора ветки с её именем и что проверено.

## Проверка ветки перед мёрджем

1. Посмотреть изменения: `git fetch origin <ветка> && git diff main..origin/<ветка>`
2. Перепроверить типы и тесты тем же способом, что и автор (CLAUDE.md, «Рабочий цикл», шаг 3) — не доверять на слово.
3. **Для рискованных изменений** (миграция схемы, деньги, права доступа, новый внешний сервис, что угодно, что стоит увидеть в браузере) — поднять ветку в изолированном стенде на этом же сервере, не трогая прод:

   ```bash
   cd /opt/ihelp.am
   git worktree add ../ihelp.am-staging origin/<ветка>
   cd ../ihelp.am-staging
   cp /opt/ihelp.am/.env .env
   # свой проект compose, свои порты — прод и соседи не задеты; та же docker-compose.yml — тот же стек 1 к 1
   export COMPOSE_PROJECT_NAME=ihelp-staging HTTP_BIND=8081 HTTPS_BIND=127.0.0.1:8444 APP_URL=http://<IP-сервера>:8081
   docker compose up -d --build
   ```

   Отдельные тома (`ihelp-staging_pgdata` и т.д.), отдельная база — от прод-данных изолировано полностью. Если ветка меняет `prisma/schema.prisma`, миграция сначала прогоняется здесь, на этой копии, а не на проде.

   **Осторожно:** если скопировать `.env` как есть, стенд будет слать настоящие сообщения через настоящие токены (Telegram-бот, WhatsApp, Resend) — это те же самые ключи, что и в проде. Для проверки сценариев с уведомлениями либо очистите соответствующие поля в staging-`.env`, либо явно предупредите, что тест реальный.

   Убрать стенд после проверки:
   ```bash
   cd /opt/ihelp.am-staging && COMPOSE_PROJECT_NAME=ihelp-staging docker compose down -v
   cd /opt/ihelp.am && git worktree remove ../ihelp.am-staging
   ```

## Мёрдж и выкладка

1. `cd /opt/ihelp.am && git checkout main && git pull`
2. `git merge --no-ff origin/<ветка>`
3. Если ветка меняла `prisma/schema.prisma` — бэкап перед выкладкой обязателен отдельно (как и раньше, CLAUDE.md правило 5): `docker compose exec -T backup sh /backup.sh once`
4. `git push origin main`
5. `deploy/update.sh` — бэкап, сборка, миграции, smoke-тест, проверка соседей. Если упало — прод не пострадал, разбираться можно не спеша.
6. Удалить смёрдженную ветку: `git push origin --delete <ветка>`
7. В задаче Control Center — статус «Готово», комментарий с итогом выкладки (что подтвердил smoke-тест).

## Если ветка не годится

Не мёрджить. Комментарий в задаче — что не так, статус обратно «Бэклог» (доработать) или «Заблокирована» (нужно решение). Ветку в репозитории можно оставить — автор поправит и попросит проверить снова.

## Дальше

Ручной `git worktree` + параметризованный `docker compose` выше — рабочий, но ручной способ. Обёртка одной командой (`deploy/staging.sh`) — отдельная задача в бэклоге, не сделана. Полноценный постоянно работающий тестовый стенд с обезличенными данными (задача **DB-6**) — более тяжёлый и дорогой вариант той же идеи (отдельный ресурс на сервере постоянно, а не по требованию); изолированный стенд выше закрывает ту же потребность без этого расхода уже сейчас.
